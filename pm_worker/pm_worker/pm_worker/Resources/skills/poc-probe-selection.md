## Purpose
原型不是越像越好，是为验证假设服务的：灰盒线框验信息架构、关键流程可点击验走通性、仿真界面验价值感知。精度每升一档成本翻倍，而很多假设用灰盒就能证伪。本技能在动笔前把「验证什么假设、谁来评审、用哪种形态」对齐，让原型预算花在刀刃上——这是「灰盒线框风即可」这类度选择判断的依据。

## 步骤
1. 列出本版本待验证假设，按「不成立的代价」排序，标注类型：信息架构类（用户找得到吗）/ 流程可用性类（走得通吗）/ 价值感知类（觉得有用吗）
2. 每条假设映射原型形态：
   - 信息架构类 → 灰盒线框（布局与层级，无视觉）
   - 流程可用性类 → 关键流程可点击（跳转与状态流转）
   - 价值感知类 → 仿真界面（真实文案、数据与视觉）
3. 按评审对象校准：用户测试避免过度仿真（反馈被视觉吸走）；开发评审补数据流与状态说明，而非堆像素
4. 每页原型标注承载的假设编号，与假设清单一一对应；无假设认领的页面砍掉
5. 产出物与模块-页面映射表逐页对齐；记录各页形态与度
6. 验证结论回写：每条假设标记「已验证 / 已证伪 / 待验证」

## 反模式
- **一上来做高保真**：从视觉稿开始画，两周后才发现核心流程走不通——灰盒就能验证的假设不配仿真精度。先低后高，低档证伪的假设直接省掉高档成本。
- **逼真度错配**：给用户测试看灰盒，反馈全是「太丑不敢用」（视觉劝退）；给开发看像素级仿真却不给数据流与状态说明（逼真度给错了维度）——形态跟随评审对象与假设类型，不是全局统一精度。
- **原型假设漂移**：画着画着顺手加设置项、加动效，页面越加越多——每个新增页面都要过「验证哪条假设」，答不上来不加。漂移的原型验证不了任何东西，只是提前做了半成品。

## 一个例子
健身App v1.1 原型：核心假设「打卡→周报的坚持反馈闭环能被小白感知为价值」属价值感知类，周报页做仿真界面（真实文案：本周对比上周、连续天数外显、缺数据不编造）；「打卡主流程五步内完成」属流程可用性类，打卡流程做关键页可点击；设置页、历史记录页属信息架构类，灰盒线框即可。页面清单与映射表逐页对齐，每页标注假设编号；验证结论（周报首屏文案是否引发「被看见」感）回写假设清单。
