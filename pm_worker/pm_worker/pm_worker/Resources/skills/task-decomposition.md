## Purpose
方案到执行之间隔着一层翻译：写方案的人默认的上下文，执行的人多半没有。任务拆解假设执行者「技能合格但零上下文」，把方案翻译成每个都自带验收标准的细任务——粒度小到完成与否一眼可判，进度与风险才有可观测的载体。这是 PRD 里程碑与实施计划章节的写法约束。

## 步骤
1. 先定结构边界：哪些模块/页面/接口新增或改动、各自职责一句话，结构定了再拆任务
2. 按依赖排序拉任务链，每个任务独立可交付，交付即可验收
3. 粒度压到单动作级（理想半天内）：「写完成登录页验收标准」是任务，「做登录功能」不是
4. 每个任务写清三件事：动哪里（模块/文件/系统）、验收什么（可判定标准）、依赖谁
5. 每任务自带验证步骤：执行什么、看到什么结果算过
6. 砍冗余：两个任务产出重复即合并；不为「以后可能用」预留任务

## 反模式
- **粒度过粗**：「开发周报模块」一个任务挂两周三个人——做到第三天说不清完成了百分之几，风险暴露永远滞后。粒度就是进度条，拆到单动作级。
- **假设执行者有上下文**：任务只写「优化数据模块」，不同执行者脑补出三个版本，验收时互相指责。路径、验收、依赖必须写进任务，默认读的人什么都不懂。
- **先拆任务后定结构**：模块边界没定就开拆，任务各自成立、拼起来打架，返工以「联调问题」的名义出现。结构先行是拆解第一步，不是锦上添花。

## 一个例子
健身App 周报功能拆解：先定结构（数据采集 / 报告生成 / 推送三模块），再拉任务链——①写周报验收标准（Given 本周 3 次训练，When 周日 20 点，Then 收到含完成率与趋势图的周报）→ ②接健康数据读取（验收：模拟器读出 7 天样本）→ ③生成逻辑 → ④推送与降级路径。每任务半天内、独立验收，第三天就能说清完成了 60%。
