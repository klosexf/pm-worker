## Purpose
功能需求最常见的两种病：写给开发看的是「系统应当……」（无用户视角），写给评审看的是「提升用户体验」（不可验收）。用户故事用 Mike Cohn 三段式（As a… I want… So that…）锚定用户价值，用 Given-When-Then 验收标准保证每条需求可判定——PRD 里每条故事都能直接转成开发任务与测试用例。

## 步骤
1. 每条功能写三段式：As a <角色> I want <行为> So that <价值>——角色必须来自画像，价值必须可感知
2. 自检套壳：把 As a 句式遮住，剩下的若仍是「系统应当」，重写
3. 验收标准逐条写 Given-When-Then：Given <前置状态> When <操作> Then <可观察结果>
4. 每条 Then 必须可判定——出现「流畅、美观、智能」等不可测词即改写为可观察行为
5. 工作量超过一个迭代的故事拆分：按流程步骤、按规则、按数据边界切
6. 与模块-页面映射表对账：每条故事标注对应页面与流程节点

## 反模式
- **故事写成功能说明书**：「作为用户，我希望系统每日生成周报，以便系统数据被利用」——价值句写的是系统获益不是用户获益，角色句是万能套壳。判据：So that 的主语必须是用户，且删掉功能名后价值仍然成立。
- **验收标准不可测**：「界面美观、生成流畅」作为 Then 无法判定——QA 无法执行，验收退化为主观互评。可测改写：「When 打开周报，Then 3 秒内完成渲染，本周完成天数与打卡记录一致」。
- **史诗当故事交付**：「作为小白我想要完整的周报功能」拆不出迭代边界、验收只能整体看——一个故事一个迭代内做不完就必须拆（先出纯文本周报、再出趋势图、再出分享卡），拆分本身是排期依据。

## 一个例子
健身App 周报自动生成，PRD 中的故事：作为健身小白，我想在每周日晚收到自动生成的训练周报，这样我不用自己记录也能看见自己坚持的轨迹。验收标准：Given 本周有打卡记录，When 周日 20:00 触发，Then 生成周报并推送；Given 本周打卡满 5 天，Then 周报首屏外显连续天数与本周对比；Given 本周零打卡，Then 周报文案切换为无压力的召回语气（不出现「断签」字样）。对应页面：周报页（映射表 P0）。
